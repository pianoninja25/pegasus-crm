# Pegasus CRM — Backend Planning Document

> Working document for the team to discuss the backend architecture for Pegasus CRM.
> The frontend is complete and running on mock data. This doc captures the current
> state and proposes a backend stack. Nothing has been built yet.

---

## 1. Executive summary

**What we have:** a feature-complete Next.js 15 frontend for a multi-tenant SaaS
serving HVAC / AC service businesses (customers, engineers, quotations,
contracts, work orders, invoices, expenses, dashboards, superadmin console).
All data is generated by a deterministic PRNG (`mulberry32`) — 100% mock.

**What we need:** a real backend to persist data, handle auth, store files
(photos / PDFs), enforce multi-tenant isolation, run background jobs, and
generate documents.

**Deployment target:** self-hosted on our own VM (not Vercel / not a managed
cloud DB).

**Recommended stack (top-line):**

- Next.js API (Route Handlers + Server Actions) in the same repo as the frontend
- PostgreSQL (self-hosted in Docker)
- Drizzle ORM
- Better Auth
- MinIO (self-hosted S3) or Cloudflare R2
- BullMQ + Redis for background jobs
- Caddy reverse proxy (auto HTTPS)
- Docker Compose to orchestrate the whole box
- Resend for outbound email

**Rationale, alternatives, and trade-offs are detailed below.**

## 2. What the app is today

A multi-tenant SaaS for HVAC / AC service businesses. Two surfaces:

- **`/admin`** — platform-level superadmin console (tenants, cross-tenant users,

## 4. Current data flow (no backend)

```
seed.ts (mulberry32 PRNG)
   ↓ generates
in-memory arrays (customersStore, quotationsStore, …)
   ↓ read/written by
features/service/hooks.ts (useCustomers, useCreateCustomer, …)
   ↓ TanStack Query wraps with delay()
React components
```

Everything is deterministic and resets on page reload. `features/service/hooks.ts`
is already **API-shaped** — every hook is an async function, which means swapping
`delay()` for `fetch()` is mostly mechanical, one hook at a time.

## 5. What requires a backend

### 5.1 Persistence

Every entity in `features/service/types.ts` and `features/platform/types.ts`
needs a real database. Every table needs a `tenant_id` column + row-level
isolation.

| Entity | Source file |
|---|---|
| `AppUser`, `Tenant`, `Company`, memberships | `platform/types.ts`, `service/types.ts` |
| `Customer`, `AcUnit` | `service/types.ts` |
| `Quotation`, `QuotationLine` | `service/types.ts` |
| `ServiceContract` | `service/types.ts` |
| `ServiceVisit`, `ChecklistItem` | `service/types.ts` |
| `Invoice`, `Expense` | `service/types.ts` |
| `AppNotification` | `service/types.ts` |

### 5.2 Authentication & authorization

Currently mocked in `features/auth/authStore.ts` (Zustand + localStorage).

Backend must provide:
- Session management (login, logout, refresh)
- Password hashing / magic links / OAuth
- Tenant membership resolution (`superadmin` vs tenant-scoped roles)
- Role checks: `superadmin | administrator | manager | admin_staff | engineer`
- Tenant invites + seat management (`Tenant.plan.seats`)
- Guard middleware on every route handler

### 5.3 File / object storage

- **Service photos** — `ServiceVisit.photos[]` (before/after)
- **Customer signatures** — captured on work order completion
- **Company brand assets** — logo, stamp, signature, bank details
- **Generated PDFs** — quotations, invoices, contracts
- **Per-tenant storage quota metering** — the `StorageCategory` breakdown
  already modeled in `features/platform/types.ts` (photos / database /
  documents / logs) needs real byte counting

### 5.4 Document generation (server-side)

- Quotation PDFs — move `@react-pdf/renderer` server-side so PDFs are
  persistent, shareable via URL, attachable to emails
- Invoice PDFs — not yet built, will need same treatment
- Contract PDFs — same

### 5.5 Business logic that must live server-side

- **Customer lifecycle derivation** (`prospect | active | vip | dormant`) —
  currently computed client-side, needs to be a DB view or scheduled recompute
- **Quotation / invoice / contract number generation** — monotonic per-tenant
  sequences
- **Auto-generation of scheduled visits** from active contracts (based on
  `ServiceFrequency`)
- **Overdue detection** — invoices past `dueAt`, work orders past
  `scheduledAt`, contracts past `endDate`
- **Reports / analytics** — service mix, revenue by month, top customers,
  engineer KPIs, P&L. Currently client-side; should be SQL aggregations
- **Storage quota calculation** — per-tenant, per-category byte sum

### 5.6 Notifications

Currently `seedNotifications` — pre-baked. Backend must **generate** them:
- `upcoming_service` — visits scheduled within N days
- `expiring_contract` — contracts within 30 days of `endDate`
- `quotation_expiring` — sent quotations near `validUntil`
- `outstanding_payment` — overdue invoices
- `engineer_assigned` — visit assignment
- `daily_schedule` — morning digest per engineer
- `overdue_maintenance`, `renewal_reminder`

Delivery: in-app (SSE or polling), email digest, and optionally push (later).

### 5.7 Communications

- **Email** — quotation sent, invoice reminders, tenant invites, magic links,
  notification digests
- **WhatsApp** — current flow is `wa.me` client link; a real backend
  integration would use the WhatsApp Business API for one-tap send
- **PDF attachments** — server-generated URL that email / WA can point at

### 5.8 Multi-tenancy (control plane)

- Tenant CRUD (create, suspend, change plan)
- Cross-tenant user management (superadmin only)
- Plan / seat enforcement
- Storage quota enforcement (block uploads past limit)
- Trial expiry handling (`Tenant.trialEndsAt`, `Tenant.status`)

### 5.9 Scheduled / background jobs (cron)

- Nightly: recompute customer lifecycles, generate upcoming-visit
  notifications, mark overdue invoices
- Daily: engineer morning schedule digest email
- Weekly: contract renewal reminders
- Continuously: recount tenant storage usage

### 5.10 Search & filters

URL-persisted filters on customers / quotations / work orders / invoices
currently filter client-side arrays. Backend needs indexed queries
(Postgres `pg_trgm` + FTS is enough at this scale).

## 7. Backend language decision

**Question we asked:** Next.js (TypeScript) vs Go vs Python — which is better?

**Answer:** Next.js (TypeScript) wins clearly for this project.

### Comparison

| | Next.js (TS) | Go | Python (FastAPI) |
|---|---|---|---|
| Type-sharing with frontend | Native — `features/service/types.ts` becomes the single source of truth | Need OpenAPI / Connect codegen | Same problem — codegen from OpenAPI |
| Raw request throughput | Good | Best (5–10×) | Decent (async) |
| CPU-bound work (PDFs, big reports) | Weak — needs worker offload | Great | Weak (GIL) — needs workers |
| Multi-tenant SaaS auth libs | Better Auth / Clerk / Auth.js — org-first | Assemble yourself (Ory, custom JWT) | Assemble yourself (fastapi-users, Authlib) |
| ORM story | Drizzle / Prisma | sqlc, Ent, Bun | SQLAlchemy 2.0 |
| Concurrency model | Event loop | Goroutines | Async or workers |
| Deploy DX | Simple (`next start`) | Single binary | Docker + Python runtime |
| Hiring / onboarding | Same skill as frontend | Extra hire | Extra hire |
| ML / data science reach | Meh | Meh | Best |

### Why Next.js wins specifically here

1. **We already have a 900-line TS domain model** in `features/service/types.ts`.
   With Go or Python we'd either write it twice or bolt on OpenAPI codegen. With
   Next.js the schema in `db/schema.ts` (Drizzle) *is* the type.
2. **`features/service/hooks.ts` is already shaped like an API client.** Every
   mock function has the signature of a real endpoint. Swapping `delay()` for
   `fetch()` is mechanical.
3. **Multi-tenant auth is the hardest part, and Better Auth solves it in TS.**
   Go and Python have no equivalent of Better Auth's org + membership + role
   primitives. We'd hand-roll it.
4. **The workload is CRUD + files + reminders.** Nothing here is
   throughput-bound or CPU-bound in a way Go would help. The one CPU-heavy
   thing (PDF generation) belongs in a background job regardless of language.
5. **Small team, one language, one deploy.** Splitting stacks is a real tax —
   CI, envs, deployment, error tracking, secrets, local dev — all doubled.

### When we'd add Go or Python later (as a sidecar)

- **Go sidecar** if we add real-time telemetry from IoT-connected AC units
  (MQTT / WebSockets, thousands of concurrent connections).
- **Python sidecar** if we add predictive maintenance, OCR on receipt uploads,
  or heavy pandas-driven reports.

Both cases: small focused service **alongside** the Next.js API, not instead of.

## 8. Database decision

**Choice: PostgreSQL (self-hosted in Docker).**

- Rich relational domain (foreign keys everywhere) — SQL is the right shape.
- Native lat/lng, JSONB (checklist, photos), full-text search.
- Row-Level Security (RLS) gives us per-tenant isolation enforced at the DB,
  not the app.
- No NoSQL — the data model rules it out.

### Neon vs self-hosted Postgres

We originally considered **Neon** (serverless Postgres) because it pairs
naturally with Vercel. Once we decided to deploy on our own VM, **Neon's
advantages evaporate**:

| Neon strength | Applies to our setup? |
|---|---|
| Scales to zero on idle | No — we have a long-lived Node process |
| HTTP driver for serverless functions | No — regular TCP connection is fine |
| Database branching per PR | Nice but not worth the vendor tie |
| Zero ops | We accepted ops when we chose self-hosted |

**Conclusion:** run Postgres in Docker on the same VM. Cheaper, faster (no
network hop), no external dependency.

## 9. ORM decision — Drizzle

**Choice: Drizzle ORM.**

Drizzle is a thin, type-safe TypeScript ORM. Schema defined in TypeScript,
compiles to plain SQL, generates migrations by diffing the schema.

### Why Drizzle for this project

1. **Types flow both ways.** `db.select().from(customers).where(...)` returns a
   row typed exactly like our `Customer`. No `any`, no codegen step.
2. **No engine binary.** Prisma ships a Rust binary (~15 MB) that needs a
   `prisma generate` step on every schema change. Drizzle is pure TS.
3. **Works with any Postgres.** Neon, self-hosted, RDS — doesn't care.
4. **Drop to raw SQL any time.** `sql\`...\`` template for window functions,
   CTEs, PostGIS. Prisma fights us on that.
5. **Migrations are plain SQL files.** Reviewable in PRs, hand-editable.

### Alternatives considered

| Option | Why not (for us) |
|---|---|
| **Prisma** | Popular but heavier (Rust engine, codegen step, opaque migrations); Drizzle is more Postgres-idiomatic. Prisma is still fine — pick it if the team already knows it. |
| **Kysely** | Query builder only, no schema definition. More manual for a domain this size. |
| **Raw SQL + `pg`** | No ORM. Fine for small backends, painful with 20+ tables and a solo dev. |

## 10. Deployment decision — self-hosted VM

The team has decided we deploy on our own VM. That changes several picks
compared to a Vercel-hosted setup.

### Revised stack for self-hosted

| Layer | Vercel version | Self-hosted version |
|---|---|---|
| Runtime | Vercel serverless | `next start` in Docker on the VM |
| DB | Neon (serverless) | PostgreSQL in Docker on the VM |
| ORM | Drizzle | Drizzle (unchanged) |
| Auth | Better Auth | Better Auth (unchanged) |
| Object storage | Cloudflare R2 | MinIO in Docker, or keep R2 |
| Background jobs | Inngest (cloud) | BullMQ + Redis in Docker |
| Cache / queue | — | Redis in Docker |
| Reverse proxy + HTTPS | Vercel edge | Caddy (auto Let's Encrypt) |
| Email | Resend | Resend (unchanged — never send from a VM) |
| Orchestration | — | Docker Compose |
| Optional PaaS layer | — | Coolify or Dokploy |
| CI/CD | Vercel git integration | GitHub Actions → GHCR → SSH deploy |

### What the VM ends up running

A single `docker-compose.yml`:

```
├── app          # next start — the Next.js app
├── postgres     # database
├── redis        # queue + cache
├── minio        # S3-compatible object storage (or use R2 instead)
├── caddy        # reverse proxy + auto HTTPS
└── (worker)     # optional separate BullMQ worker process
```

### Sizing (initial guess)

- **$10–15/mo VPS** (Hetzner CX22, DigitalOcean 2 GB, Vultr HF) handles this
  comfortably for a few tenants and thousands of records
- **$25–40/mo** (4 GB RAM, 2 vCPU) once we have real users and photo uploads
- Add a second small VM for Postgres later if we outgrow one box

## 11. Final recommended stack

| Layer | Choice | Notes |
|---|---|---|
| Frontend | Next.js 15 (unchanged) | Already built |
| API | Next.js Route Handlers + Server Actions | Same repo, share types |
| Validation | Zod | Shared between client forms and server routes |
| Language | TypeScript | Single language across the stack |
| DB | PostgreSQL in Docker | On the app VM (or a nearby DB VM) |
| Multi-tenancy | Postgres Row-Level Security + `SET LOCAL app.tenant_id` per request | Isolation enforced at the DB |
| ORM | Drizzle | Type-safe, no engine binary |
| Migrations | Drizzle Kit (SQL diff files) | Reviewable in PRs |
| Auth | Better Auth | Organizations, memberships, roles, magic links, OAuth |
| Sessions | Better Auth (DB-backed) | Rotated on privilege change |
| Object storage | MinIO (self-hosted) or Cloudflare R2 | See open question |
| PDF generation | `@react-pdf/renderer` server-side | Store outputs in object storage |
| Background jobs | BullMQ + Redis | Cron, retries, DLQ |
| Email | Resend + React Email | Templated, testable |
| Realtime (later) | Postgres LISTEN/NOTIFY + SSE | Skip for MVP; poll TanStack Query |
| Search | Postgres `pg_trgm` + FTS | Sub-100k rows per tenant |
| Reverse proxy + HTTPS | Caddy | Auto Let's Encrypt |
| Orchestration | Docker Compose | One file describes the whole box |
| Optional PaaS UI | Coolify or Dokploy | Nice to have, not required |
| Observability | Sentry + `docker logs` initially; Loki/Grafana later | Errors first |
| CI/CD | GitHub Actions → GHCR → SSH deploy | Or `git pull && docker compose up -d --build` |

### Concretely, how the frontend swaps to real API

Every mock hook in `features/service/hooks.ts` becomes:

- `useCustomers()` → `GET /api/customers` (Route Handler) → Drizzle →
  RLS-scoped query → typed response
- Mutations → Server Actions (`"use server"`) that reuse the same Zod schemas
- Types stay in `features/service/types.ts`
- DB schema in `db/schema.ts` derives to the same shape

## 12. Trade-offs of self-hosting

Be honest with the team before committing.

**What we gain**
- Flat monthly cost, no per-request billing surprises
- No vendor lock-in
- No cold starts, unlimited compute
- Full control of the box

**What we take on**
- **Backups** — nightly `pg_dump` off-box (30 lines of shell + cron)
- **Upgrades** — OS patches, Postgres major upgrades every couple of years
- **Monitoring** — Uptime Kuma (self-hosted) or Better Stack (free tier)
- **Log aggregation** — Loki + Grafana, or `docker logs` for a while
- **Certificate renewal** — Caddy handles this automatically (free)
- **Security patches** — need someone paying attention to CVEs

**Cost of managed alternatives, for comparison**
- Vercel Pro: ~$20/user/mo + serverless usage
- Neon: free tier fine to start, ~$19/mo Launch plan
- R2: $0.015/GB/mo storage, no egress fees

We're trading ops work for ~$40–80/mo saved and full control.

## 13. Rollout order

Once the stack is approved:

1. **Infra scaffolding**
   - `docker-compose.yml`, `Dockerfile` for the Next.js app, `Caddyfile`
   - Local dev via `docker compose up`
2. **DB foundation**
   - Drizzle schema mirroring `features/service/types.ts`
   - Postgres RLS policies for tenant isolation
   - Seed script to load the existing mock data into the DB (so dev feels
     identical to today)
3. **Auth**
   - Better Auth wired to `users` + `tenants` + `memberships`
   - Replace mock `authStore` with a real session
4. **Superadmin surface first**
   - Tenants CRUD, seat / plan management (smallest domain)
5. **Tenant-scoped read APIs**
   - Customers, quotations, work orders, invoices, expenses — swap
     TanStack Query hooks one by one
6. **Mutations + file uploads**
   - S3-compatible presigned uploads (MinIO / R2)
   - Storage quota metering
7. **Background jobs**
   - BullMQ + Redis
   - Notification generators, contract-to-visit expansion, overdue detection,
     storage recount
8. **Server-side PDFs**
   - Move `@react-pdf/renderer` to a route handler
   - Persist PDFs in object storage, shareable via URL
9. **Email**
   - Resend + React Email templates
10. **Reports**
    - Replace client-side aggregation with SQL views / route handlers

## 14. Open decisions for the team

1. **MinIO vs Cloudflare R2 for file storage?**
   - MinIO on the same VM = one bill, one box, but photos die if the VM dies
     until backups restore
   - R2 = 3¢/GB/mo, no egress fees, off-box durability, still works from
     our VM. Recommended unless the team has a "everything on our hardware"
     preference.

2. **Coolify / Dokploy vs raw Docker Compose?**
   - Raw Compose = simplest, most control, SSH-based deploys
   - Coolify = web UI, one-click deploys, DB backups, log viewer, monitoring —
     recommended if we want to spend less time on ops

3. **Auth features on day one?**
   - Email + password only
   - Magic link + Google OAuth (recommended)
   - Email/password + OAuth + passkeys
   - Add SAML SSO later for Enterprise tier

4. **Scope of the first backend milestone?**
   - Foundation only: DB schema + auth + tenants + superadmin (recommended)
   - Foundation + all read APIs (mutations still mocked)
   - Full MVP: everything CRUD + uploads + PDFs + one background job

5. **VM provider?**
   - Hetzner (cheapest, EU-based)
   - DigitalOcean (most familiar)
   - Vultr / Linode / OVH (options)
   - Existing infra we already run on

6. **Do we want a staging environment?**
   - Same VM, second Docker Compose project on a subdomain
   - Separate VM
   - Just prod

7. **Redis for what beyond BullMQ?**
   - Rate limiting? Session cache? Search suggest cache?

## 15. Non-goals (for now)

Explicitly out of scope for the first backend milestone, listed so the team
doesn't expect them:

- Real-time WebSocket updates (poll via TanStack Query is enough)
- WhatsApp Business API integration (keep `wa.me` deep-link)
- Mobile / PWA offline sync
- IoT ingestion for connected AC units
- SSO / SAML
- Kubernetes / auto-scaling infra
- Multi-region deploy

Any of these can be added later without redoing the foundation.
